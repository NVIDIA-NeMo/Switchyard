6//! # libsy — multi-LLM agent optimization (routing first)
7//!
8//! `libsy` decides, per request, *how* to serve an LLM call: which model(s) to
9//! invoke, in what order, and how to combine the results. Routing is the first
10//! and simplest case; the same interfaces also express classifier routing,
11//! ensembles, cascades, and other optimizations. The library owns no HTTP client
12//! and no provider SDK — it decides, and the host makes (or is asked to make) the
13//! actual calls — so it embeds cleanly in a proxy, gateway, or agent runtime.
14//!
15//! ## Quick start
16//!
17//! The [`Noop`] algorithm verifies host integration without making an upstream call:
18//!
19//! ```no_run
20//! use std::sync::Arc;
21//! use switchyard_libsy::{Algorithm, Noop};
22//! use switchyard_protocol::{Context, Request, text_request};
23//!
24//! # async fn example() -> switchyard_libsy::Result<()> {
25//! let algorithm: Arc<dyn Algorithm> = Arc::new(Noop {});
26//! let request = Request {
27//!     llm_request: text_request(Some("switchyard/noop".into()), "hello"),
28//!     ..Request::default()
29//! };
30//! let (_decisions, response) = algorithm.run(Context::default(), request).await?;
31//! assert_eq!(response.selected_model(), Some("switchyard/noop"));
32//! # Ok(())
33//! # }
34//! ```
35//!
36//! ## The model
37//!
38//! - An [`Algorithm`] is the optimization *algorithm*. Its
39//!   [`create_run_task`](Algorithm::create_run_task) runs once per request
40//!   and makes as many model calls as it needs — via [`Driver::call_llm_target`], which look
41//!   like ordinary calls — publishes its [`Decision`](switchyard_protocol::Decision)s with [`Driver::info`], and
42//!   returns the final [`Response`](switchyard_protocol::Response). The provided
43//!   [`run_stream`](Algorithm::run_stream) drives that on its own task and hands
44//!   back a stream of [`Step`]s; [`run`](Algorithm::run) runs
45//!   it to completion with the targets' default clients.
46//! - An [`LlmTarget`] names a routing target by its [`semantic_name`](LlmTarget::semantic_name).
47//!   Every call is *offloaded* to the request's stream as a [`Step::CallLlm`]; the
48//!   target's [`RoutedLlmClient`](switchyard_protocol::RoutedLlmClient), if any, rides along as
49//!   [`RoutedRequest::default_client`] so the host can serve it by default or
50//!   override it (see below).
51//!
52//! ## Running a request
53//!
54//! Hold the algorithm as `Arc<dyn Algorithm>` and call one of two provided methods:
55//!
56//! - [`run`](Algorithm::run) — run to completion, serving each
57//!   offloaded call via its [`RoutedRequest::default_client`], and return the decision
58//!   trace plus the final [`Response`](switchyard_protocol::Response). The simplest integration; use it when the
59//!   algorithm holds the model clients (it errors if a routed target has no client).
60//! - [`run_stream`](Algorithm::run_stream) — return a stream of [`Step`]s. Each
61//!   model call is offloaded: the stream yields a [`Step::CallLlm`] carrying a promise;
62//!   the host performs the real model call (optionally via the promise's
63//!   `default_client`) and fulfills it with [`CallLlmRequest::respond`]. Decisions
64//!   arrive as [`Step::Decision`] as the algorithm makes them, and the run ends with a
65//!   [`Step::ReturnToAgent`] carrying the final response. The step stream is bounded,
66//!   so pulling it paces the algorithm one step at a time — an "ask, don't call" mode
67//!   that lets a host that owns its transport keep control of every call.
68//!   Pass `None` for its optional observer when per-call observations are not needed.
69//!
70//! ## Concurrency
71//!
72//! [`Algorithm::create_run_task`] takes `self: Arc<Self>`, so one shared
73//! `Arc<dyn Algorithm>` (no lock) serves many requests in parallel. Each
74//! [`run_stream`](Algorithm::run_stream) call builds its own [`Driver`], so
75//! offloaded calls never cross between concurrent requests. An algorithm is
76//! responsible for its own thread-safety — stateless (like the reference routers) or
77//! interior mutability over just its own state.
78//!
79//! ## Observability
80//!
81//! The provided run methods instrument every algorithm from the outside — at the
82//! [`Decision`](switchyard_protocol::Decision) hook and the offload boundary — so algorithms carry no telemetry
83//! code. Each run gets a `libsy.run` tracing span (correlation ids from
84//! [`Metadata`](switchyard_protocol::Metadata) attached) with a child `libsy.llm_call` span per model call
85//! (fulfillment time as the algorithm observes it) plus a `libsy.client_call`
86//! span around the actual API call when [`run`](Algorithm::run) serves it;
87//! each [`Driver::info`] decision is logged with its reasoning; and OpenTelemetry
88//! metrics record run/call counts, latency, and published decisions, keyed by
89//! [`Algorithm::name`] plus `selected_model` and `outcome`.
90//! Metrics use the global meter provider and spans/logs the `tracing` facade: a
91//! host that installs an OTel SDK and a `tracing` subscriber (bridged with
92//! `tracing-opentelemetry` for OTLP spans) gets the full signal set; with
93//! neither installed, everything is a no-op.
94//!
95//! ## Algorithms
96//!
97//! Concrete algorithms are exported from the crate root:
98//!
99//! | Algorithm | Purpose |
100//! |---|---|
101//! | [`Noop`] | Return a fixed local response without making a model call. |
102//! | [`Passthrough`] | Always call one configured target. |
103//! | [`Random`] | Select among any number of targets using uniform or weighted routing. |
104//! | [`LlmTaskClassifier`] | Ask a judge model to choose an efficient or capable target. |
105//! | [`StageRouter`] | Route coding-agent turns from tool and progress signals, with an optional judge fallback. |
