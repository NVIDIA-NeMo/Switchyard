    Routing Overview¶

    The switchyard-server binary loads a native TOML deployment. Each route's id becomes a model ID available through OpenAI Chat Completions, Anthropic Messages, and OpenAI Responses requests.

    Use this page to choose a routing strategy, then open its detailed page for configuration and tuning. Mechanics of Libsy explains the execution model; Switchyard Protocols explains the request and response data.

    Choose a strategy¶

    Start with Auto. Choose Task or Execution when you want more control over how requests move between an efficient model and a capable one.

    Choice Use it when Route type
    Auto You want Switchyard's recommended preset. auto
    Task You want an LLM to judge which model can handle the task. llm_classifier
    Execution You want tool results and agent progress to guide each request. stage_router

    Task uses the LLM classifier's capability mode. Its classify_trigger setting controls whether the judge runs for each request, each user turn, or once per session. Execution uses the stage router, which reads tool-result history and can optionally call an LLM judge. The TOML configuration keys are unchanged.

    Whichever strategy you choose, the two models you put behind it matter more than any threshold. See Model Selection. To tune cost against quality, follow the tuning loop.

    What the names mean¶

    Name Route type What it does
    Auto auto The Execution preset with fixed settings.
    Task llm_classifier, mode = "capability" A judge reads the task before the turn is served and picks the strong or weak model.
    Execution stage_router Tool results from the last few turns pick the capable or efficient model for each turn.
    Composite composite A judge picks the starting tier at each user turn. Execution runs the turns in between.
    Plan/Execute plan_execute The capable model plans. The first file edit hands the session to the efficient model.
    Escalation llm_classifier, mode = "escalation" The weak model serves until a judge reports the same failure on consecutive turns. Then the session latches to the strong model.
    Custom llm_classifier, mode = "custom" Your own judge prompt and schema choose among any number of targets.
    Advisor Gate advisor One executor serves every turn. A stronger advisor reviews its plans and "done" claims.
    Verification-Gated vgr An efficient model drafts. Verified answers stay on the efficient tier, and everything else goes to the capable model.
    Prefill prefill_router A classifier you train on the prompt's hidden states picks the target. Experimental: Switchyard supplies no checkpoint, exporter, or encoder assets.
    Random random A fixed traffic split.
    Fixed passthrough One target, no decision.
    Sub-agent subagents table A separate policy for delegated sub-agent work on passthrough, stage_router, and composite routes.

    Every route streams the served model's reply. Three hold a turn back first. Escalation buffers the weak reply until the judge rules on it. advisor holds a gated turn until the review finishes. vgr holds a local candidate until it is verified. Task judges before the turn is served, which adds the judge's latency to every judged request.

    "Measured" links the Benchmarks page, the checked-in profile, or the public report a result comes from. The capable_first picker and prefill_router are experimental. See Model Selection for the measured model pairs.

    When routing will not help¶

    Each strategy page lists the cases it does not fit: stage router and escalation. These cases apply across strategies:

    • Requests carry no session ID. Escalation never latches, at any confirmations. Composite cannot retain the tier. Task with user_turn or new_session judges every request. Plan/Execute needs the first edit to stay in the request history. Execution keeps no capable hold. Send x-switchyard-session-id, or use a strategy that decides from the request alone.
    • Both tiers resolve to the same model, or the efficient model is the stronger one. Routing then only adds cost. Run the inverted-pair check first.
    • Chat-only traffic on Auto or Execution. With no tool results the signals abstain and every turn lands on the efficient tier. Use Task or Composite, which judge the request itself.
    • Responses continuations by ID. A client that sends previous_response_id with new input, and no history, hides the tool calls that Execution and Plan/Execute read. See Responses continuations by ID and the Plan/Execute history requirement.
    • A judge that cannot return schema-valid JSON. Task then sends every request to the strong target, Execution falls back to the picker default, and escalation never latches. When the provider rejects the judge request outright, escalation turns fail with that error instead. Run the structured output check and see Judge model compatibility.
    • A judge on every tool step. Task's default classify_trigger = "every_request" judges every tool continuation. An agent that makes twenty tool calls causes twenty-one judge calls for one task. Use user_turn with a session ID, or Execution, which reads the tool results without a model call. See When the judge runs.
    • Sub-agent traffic without identity. A subagents policy applies only when the harness sends sub-agent identity. Otherwise delegated requests follow the parent route. The server logs a warning for Claude Code versions known to lack child identity; other harnesses give no log line. See Sub-Agent-Aware Routing.

    Start here¶

    Three starting points. Each names a strategy, a file in this repository to copy, and the one dial to move first.

    1. A coding agent, and cost comes first. Start with auto. When you need to tune, copy the DeepSWE stage profile and move confidence_threshold as described in Tuning confidence_threshold.
    2. Long sessions where the cheap model should run until a judge reports that it is failing. Use escalation. Copy the escalation profile, send a session ID, and move confirmations as described in Tuning options.
    3. One executor you want to keep, with a stronger model as a quality gate. Use the advisor gate. Copy the DeepSWE advisor profile and move max_reviews together with gate_min_tool_results as described in Tuning.

    For multi-turn support traffic with few tool results, the tau2 custom-classifier profiles are the measured starting point. Their dial is the judge rubric in prompt.

    Auto¶

    Auto is a preset, not a separate routing algorithm. An auto route builds a stage router with these settings. It does not compare strategies at runtime.

    Setting Value What it does
    picker efficient_first The efficient tier serves a turn when the tool signals are not confident.
    confidence_threshold 0.5 How strongly the tool signals must agree before they pick a tier on their own.
    recent_turn_window 3 How many recent tool results the signals are computed over.
    capable_hold_turns 2 How many turns stay on the capable tier after an escalation, skipping signal processing and classification.
    Classifier none No LLM judge is called.

    Auto accepts no tuning keys. To change a setting, write the equivalent stage_router route shown in the TOML schema and edit it there. Choose the two models with the model selection guide.

    Only the efficient_first picker has published results. The capable_first picker is experimental.

    When Auto does not route¶

    Auto decides from tool results in the request. In these cases every request goes to one tier:

    • No tool results in the request. Chat-only requests, and the first request of an agent session, carry no tool history. The signals abstain and the efficient tier serves the turn. This is by design. GET /v1/stats counts these turns under algorithm_stats.stage_router.routing_decisions.fall_open. See Verify routing is active.
    • Both tiers name the same target. The server accepts a route whose capable_target and efficient_target are the same target. Every request then goes to that one model, and GET /v1/stats lists a single entry under .models.
    • No session ID on the request. The capable hold is kept per session. A request without a session ID gets fresh state, so a hold set by one request is gone on the next. Requests with a session ID but no agent ID share one hold within that session.

    A critical error, a repeated identical failure, or a context-compaction marker in the tool history still sends the turn to the capable tier. See decision sources.

    Auto uses the settings of the published stage-router results, with two differences: those runs set recent_turn_window = 5 and added a handoff note. Every published result comes from a coding agent whose requests carry tool results. The model selection guide lists the measured model pairs.

    Common route shape¶

    A deployment has three layers. LLM clients describe how to reach a provider, targets name models on those clients, and routes decide which target serves a request:

    schema_version = 1

[llm_clients.openrouter]
format = "openai_chat"
base_url = "https://openrouter.ai/api/v1"
api_key_env = "OPENROUTER_API_KEY"

[targets.strong]
id = "openai/gpt-4o"
llm_client = "openrouter"

[targets.weak]
id = "openai/gpt-4o-mini"
llm_client = "openrouter"

[routes.fast]
id = "fast"
type = "passthrough"
target = "weak"

[routes.smart]
id = "smart"
type = "random"
targets = ["strong", "weak"]
weights = [3, 7]

    Clients send a route's id (fast or smart) as the request's model ID. The table name in [routes.smart] is local to the file; only id is visible to clients. A single deployment can serve multiple routes on the same host and port.

    Credentials stay outside the file: api_key_env names an environment variable that is read at startup. Omit it for an upstream that needs no credential, such as a local model server.

    The examples use model IDs from the OpenRouter model catalog. Select IDs available to your account before deploying; catalog availability can change.

    Direct model routes¶

    A passthrough route registers one target under one model ID with no routing decision:

    [routes.fast]
id = "fast"
type = "passthrough"
target = "weak"

    Use a routing strategy instead when requests must be split or classified across targets. There is no catalog auto-discovery, so to expose several upstream models, add one passthrough route per model.

    Self-hosted targets¶

    Any target can point at an OpenAI-compatible model server you operate. For example, start a local vLLM server:

    vllm serve ./my-rl-qwen --served-model-name my-rl-qwen --port 8000

    Then declare it as its own LLM client and target. The client needs no api_key_env when the server does not require a credential:

    [llm_clients.local_vllm]
format = "openai_chat"
base_url = "http://localhost:8000/v1"

[targets.local]
id = "my-rl-qwen"
llm_client = "local_vllm"

[routes.local]
id = "local"
type = "passthrough"
target = "local"

    Switchyard does not start or manage the model server; it only sends requests to the configured endpoint.

    Run a deployment¶

    After installing the Rust server, as described in Local Evaluation, export the provider credential, validate the configuration, and start the binary:

    export OPENROUTER_API_KEY="your-openrouter-key"  # pragma: allowlist secret
switchyard-server --config routes.toml --dry-run
switchyard-server --config routes.toml \
  --host 127.0.0.1 --port 4000

    Send a request using a route ID:

    curl http://localhost:4000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"smart","messages":[{"role":"user","content":"hello"}]}'

    For the complete TOML schema and every route option, refer to the TOML Schema.
