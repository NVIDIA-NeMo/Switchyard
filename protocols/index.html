    Switchyard Protocols¶

    Mechanics of Libsy follows the work exchanged through run_stream. This section explains the data inside that work: an LLM conversation or a set of typed questions for a decision model.

    Both use provider-neutral Rust types from the switchyard-protocol crate. These types define Switchyard's protocols. Your application converts its inputs into these types, passes them to libsy, and converts model calls and responses at its provider boundary.

    Why use a neutral protocol?¶

    Provider APIs describe the same interactions in different ways. An Anthropic tool call is a tool_use content block. OpenAI Responses uses a function_call item. Chat Completions puts it in an assistant message's tool_calls array.

    An algorithm needs to know that the model called a tool, its name, and its arguments. A shared ToolCall gives it those facts without tying the algorithm to one provider's JSON. Your gateway or agent harness keeps control of the client, credentials, and execution.

Your model client and provider API

    The protocol crate defines the data exchanged with libsy. Conversion and network calls happen in your application or in optional Switchyard crates. When handling run_stream, your application can use any client and return the protocol response through CallModel::respond or CallDecision::respond. The crate also provides optional client traits that help Switchyard's supplied clients and execution helpers work together.

    Two kinds of model interaction¶

    Interaction Protocol fields and types Used when Read next
    LLM conversation Request.llm_request: LlmRequest; Response.llm_response: LlmResponse Your application starts a run or serves Step::CallModel. Content can include text, tools, reasoning, and media. LLM-Related Protocols
    Typed decision CallDecision.request: DecisionRequest; the work future returns libsy::Result<DecisionResponse> Your application serves Step::CallDecision. Named questions ask for a Boolean estimate, a choice, or a rubric score. Decision Model-Related Protocols

    The LLM envelopes also carry metadata: Option<Metadata>. That application metadata is separate from the provider's conversation content. Decision calls use their own request and response types directly.

    Choose who owns conversion¶

    Integration choice Use it for
    Your own adapters Convert an existing SDK's types or an in-process model's data to and from switchyard-protocol. Keep your existing client and transport.
    switchyard-translation Decode and encode supported LLM JSON and streaming events while keeping your own transport.
    switchyard-llm-client Use Switchyard's HTTP clients, including LLM translation and typed decision adapters.

    The two guide pages explain these boundaries and the integration flow. For field-level details, use the LLM request reference or decision question reference. Each reference page links back to its guide and to the next part of the exchange. For complete type and method definitions, open the protocol crate reference.
